# 原資料から読む要約：今回の変更と後日の品質確認

## 今回確認できること

通常の要約は、先に厳格な事実一覧の完成を待つ経路から、原資料を読んで要約する経路へ移す。元の文章・表・期間・単位を保持し、対応するTDnetの構造化資料が使える場合は出典情報付きで補助する。原資料の保持、数値の局所的な照合、生成した解釈は別のものとして扱う。

これにより、正しい数量の候補が拒否されたり、任意の補足整理が失敗したりしても、原資料を読む入口を残せる。参照の取り違え、推論の誤り、資料にない情報の断定がなくなることは保証しない。

このPRの評価準備はすべてオフライン。実モデル呼出しは行わない。固定応答の再生、パーサーテスト、原文が入力にあるという確認は、次に生成される要約の品質改善を証明しない。

## 実装した入口と限界

- 要約はPDF全文を直接読み、事実一覧の抽出成功を前提にしない。通常要約と追加分析は別の要求で、それぞれ1回だけ生成する。形式エラー時に自動で有料再試行はしない。
- 一覧の同じ開示行に実在するXBRLリンクがある場合だけZIPを取得する。日付一覧の巡回やリンクの推測は行わない。発行会社・開示日・文書の対応や訂正状態を確認できない場合は、理由を残してPDFへ戻る。
- iXBRLの概念名、期間、実績/予想、連結/単体、単位、尺度、符号と、HTMLの全セル・行・本文を保持する。指標名の一覧にない値も捨てない。共有辞書と列配列で重複を圧縮するが、元の情報もキャッシュへ保存する。
- 比較計算は原資料に明示された期間・単位・範囲が揃うものに限定する。年間予想から累計実績を引く計算は、加算できることを確認できる売上・利益の概念だけに絞る。EPSや比率を同じように引かない。この計算上の制約は、原文の取り込みや要約対象の制約ではない。
- 引用先が不正な論点は局所的に除外して通知する。引用先が存在することは、文章の解釈まで正しい証拠にはならない。図の画像認識/OCRや、PDFとXBRLの全数値を意味まで自動照合する機能は今回含まない。
- 原資料方式では実験的スコアを利用不可とする。スコアのために従来の抽出APIを裏で呼ばない。

列配列と共有辞書は入力上限を守るための表現であり、モデルの読解精度を上げるという検証結果ではない。日本語本文・表・iXBRLの対応を正しく追えるかも、後日の比較で確認する。

## 一番短い確認方法

後日、利用予算と対象を決めてから、まず1資料だけで旧版・新版を各3回比較する。4資料を一括実行する必要はない。新しいモデルや条件へ途中で替えず、エラーも3回の分母に残す。

1. 比較する2つのコミット・ビルドを固定する。旧版は `72d8509cb07944473973ae2b3643b22fccc7430f`、新版はこのPRの確認対象コミット。旧版のソースを書き換えて新版関数を呼ぶ比較にはしない。
2. 同じPDF、同じプロバイダーとモデル、全文抽出を使う。実験的スコアはOFF。`workflow` が `summary-and-analysis` なら、各回は「新たな要約→その要約への追加分析」を1セットとする。別の要約の分析を組み合わせない。
3. 1セットごとに「要約の診断JSONをコピー」と「表示中の追加分析の診断JSONをコピー」で保存する。失敗時はエラーに対応する診断、追加分析は「直近の追加分析の診断JSONをコピー」を保存する。画面の文章・未確認表示・エラーもテキストまたはスクリーンショットで残す。診断は保存件数/サイズに上限があるため後回しにしない。
4. 下記の `import` と `review-template` で取り込み、原PDFと表示文を照合する。`report` が新旧をまとめる。実モデルやブラウザーを評価ツールが起動することはない。

「表示」でキャッシュを開き直しても新しい試行にはならない。次の予定回は明示的な「再要約」から始める。診断の実行IDを匿名化したハッシュで同じ生成の使い回しを検出する。認証エラー、残高不足、429、時間切れ、共通の契約欠陥では残りを停止し、成功するまで補充しない。条件を変えた再調査は別の計画にする。

## 準備：APIを呼ばないコマンド

Node.js 20以上。追加パッケージは不要。以下のコマンドは `.env` を読まず、HTTP・LLMクライアントも読み込まない。引数なしは使い方だけを表示し、`--execute` / `--live` は拒否する。

```bash
node --test evaluation/scripts/deferred-quality/core.test.mjs
node evaluation/scripts/deferred-quality.mjs
```

同一キーの拡張を切り替えるため、旧版・新版の作業ディレクトリとビルドを分けて保管する。各版で通常のビルド手順を実施し、Chromeの拡張管理画面で試す版を読み込んで、TDnetページも再読み込みする。APIキーは利用者が通常の設定画面に入力する。キー入り設定JSON、`.env`、個人の診断をコミットしない。

公開ソースだけから、診断の `buildDigest` と同じ計算でビルド識別値を得られる。

```bash
node evaluation/scripts/deferred-quality.mjs digest --checkout ../tdnet-baseline
node evaluation/scripts/deferred-quality.mjs digest --checkout .
```

`evaluation/fixtures/source-first-quality-plan.example.json` を `evaluation/results/local/quality-config.json` へコピーし、新版コミットと両方のdigestを記入する。プレースホルダーのままでは計画を作れない。モデル名の例は料金や現時点の利用可能性の保証ではない。ケースは明示的に選ぶ。

- `known-pilot`: 1〜2件。最初は `cando-548129` 1件を推奨
- `known-regression`: 最大4件の明示選択。既知例なので汎化の証明にしない
- `holdout`: 別の未調査資料を、結果を見る前に期待値・PDF hash付きで `--cases` に指定する。今回の4件をholdoutと呼び替えることは拒否する

PDFをローカルで入手し、`<caseId>.pdf` としてPDF用ディレクトリに保存する。ツールはダウンロードせず、原PDFのSHA-256が合うかだけを確認する。TDnetの公開期限でURLが消えている場合は、既に保管した同一PDFが必要。

```bash
node evaluation/scripts/deferred-quality.mjs plan \
  --config evaluation/results/local/quality-config.json \
  --pdf-dir evaluation/fixtures/real-pdfs \
  --out evaluation/results/local/quality-plan.json
```

1資料×2方式×3回なら6回の「フル生成セット」。内部API要求は別に数える。例の要約＋追加分析では、旧版は最大5要求/セット、新版は最大2要求/セットの申告値なので、6セットで最大21要求。実コードが変わったら上限を確認して計画を更新する。未実行で料金を0円と決めつけない。

料金予約は最大入力token×最大要求数と最大出力tokenから、指定した単価に25%の余裕を加えて見積もる。単価または承認予算が未記入なら不明/未承認のまま。キャッシュ割引を当てにしない。これは課金の防止機構ではなく計画用の見積りで、手動の拡張操作を止めることはできない。後日の有料実行前に、対象・固定回数・実際の上限・総額を確認し、利用者の了承を得る。

## 診断の取り込みと採点

例：計画内の旧版1回目。新版は `baseline` を `candidate` に、2〜3回目は末尾を変更する。

```bash
node evaluation/scripts/deferred-quality.mjs import \
  --plan evaluation/results/local/quality-plan.json \
  --run cando-548129-baseline-1 \
  --summary evaluation/results/local/baseline-1-summary.json \
  --analysis evaluation/results/local/baseline-1-analysis.json \
  --evidence-kind live-generation \
  --out evaluation/results/local/quality-records

node evaluation/scripts/deferred-quality.mjs review-template \
  --plan evaluation/results/local/quality-plan.json \
  --run cando-548129-baseline-1 \
  --out evaluation/results/local/quality-reviews/cando-baseline-1.json
```

`--evidence-kind live-generation` は、計画作成後に実際に生成した診断を取り込むときだけ指定する。省略時は `recorded-response`（履歴/固定応答）で、品質の成功分子へ加算しない。計画より前の実行をliveとして取り込むことは拒否する。

要約が失敗して追加分析へ進めなかった場合は `--analysis` を省略する。失敗または未完了として残り、成功にはならない。計画が `summary` なら追加分析は取り込まない。

診断のPDF hash・URL・モデル・ビルド・要約と追加分析の対応を照合する。抽出前の失敗でPDF hashがない場合は「失敗、原資料同一性未確認」として保持する。診断に記録されていない温度・推論設定・出力上限は「実要求では未確認」。`settingsAttested: true` は手動確認の申告であり、ツールが検証したという意味ではない。

取り込みは先に `checkpoint.json` と要求ごとの応答/利用量を保存し、その後に任意のreviewを扱う。途中のreviewエラーでも元応答を失わない。同名を上書きしないため、誤ったreviewは別のreviewファイルで直す。取り込み済みの失敗を再実行で置換しない。拡張で診断自体の保存に失敗した場合、ここからAPI応答を復元することはできない。

採点ファイルは次を記入する。原PDFの物理ページと出力の該当箇所を `evidence` に残す。

- `rendered`: 表示できたらtrue、表示失敗ならfalse、未確認はnull
- `checks[].result`: pass / fail / unreviewed。単なる「良い回答」ではなく数量・期間・範囲・根拠・不確実性を点検する
- `actualCostUsd`: プロバイダー側で確認できた実費。わからなければnull。推測で0にしない
- `settingsAttested`: 計画の設定を手動で確認したか。診断から確認できない設定があることは別途notesに残す

```bash
node evaluation/scripts/deferred-quality.mjs report \
  --plan evaluation/results/local/quality-plan.json \
  --records evaluation/results/local/quality-records \
  --reviews evaluation/results/local/quality-reviews \
  --out evaluation/results/local/quality-comparison.json
```

レポートは読取・事実・推論・有用性・不確実性を分け、費用と時間も独立して表示する。未実行/失敗/表示失敗/圧縮による診断欠落を成功扱いにしない。チェックの分母は予定3回を含む。内部要求数は記録済みusage件数という観測下限で、APIエラーなどにより正確な要求数やtokenが不明なら不明のまま。費用不明件数、回ごとの時間を併記し、成功分だけの平均で速さを主張しない。

旧版と新版では入力表現だけでなく、要求数・推論設定・出力上限・要約方式も変わる。今回の手順は「同じPDF・モデルによる製品経路の比較」。同予算で原資料形式だけの因果効果を測る実験ではない。計画の上限が違えば `settingsMatch: false` が残る。宣言上の設定が一致しても、実際の要求設定が診断にないなら未確認と明示される。

## 固定した論点

`source-first-quality-cases.json` の数量は、公開PDFを人が確認した値。実装の出力を正解へコピーしていない。原単位・期間・連結/事業範囲・実績/予想・物理ページを持つ。数値正解の一覧と、質的な採点観点は分ける。

- キャンドゥ：主要15値の正しい候補が拒否された問題と、FC卸売4,904百万円/その他796百万円/構成比1.8%の誤対応を同時に見る。全部のゲートを外すことを正解にしない
- 安川電機：税引前25,963/25,204/65,500百万円、正のCFを純減としない、丸め残差を原文訂正や誤りと断定しない
- ファーストブラザーズ：既に読める売却益1,174,729千円を未開示としない。事業売上の合計と外部売上を混ぜない。税引前益から税引後正常利益を捏造しない。Q3のCF計算書は本当に非作成
- サーラ：営業CF悪化9,743百万円と利益進捗の両方を読む。年間予想から累計実績を引いた負の残差を会社のQ4予想と呼ばない

有用性の採点では、根拠への到達性、説明の優先順位、反証・条件・次に確認すべき情報を見る。あらかじめ好ましい投資判断、楽観/悲観の結論、特定の文体を正解にはしない。既知4資料の改善と未調査資料での性能は別であり、必要なら予算を別途決めてholdoutを後日行う。

## 検証の責務と未確認

- Nodeの6代表テスト：固定計画と料金予約、診断の同一性、チェックポイントの保存境界、失敗を残す比較、重複/省略/不明usage、キーが存在しても通信しないCLI
- 製品のパーサー/生成/保存/表示境界は既存と今回追加の製品テストが担当。評価ツールで同じ反例を複製しない
- 実PDF hashの確認は入力同一性の証拠であり、全内容の意味理解の証拠ではない
- 実API品質・未知資料での汎化・実際の費用/時間・利用者のChromeでの表示は後日の確認事項。履歴応答の取り込み確認を、新版の実生成成功とは数えない

古い `run-fact-summary.ts` は指定なしで複数ケースを有料実行し得るため、今回の手動比較を始めるために `npm run test:fact-summary` をそのまま実行しない。このオフライン手順からそのランナーを呼ぶ経路はない。
