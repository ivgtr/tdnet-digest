# TDnet Digest 分析精度向上計画

## 1. 文書の目的

本書は、`ir-pdf-radar-v0.5.1`の分析観点を参考にしながら、TDnet Digestの決算・適時開示分析精度を段階的に向上させるための実装計画を定義する。

実装中の判断のぶれを防ぐため、次を固定する。

- 採用する分析観点と採用しない挙動
- データ構造と責務の境界
- 実装順序
- 各段階の完了条件
- 精度評価方法
- ロールアウトとロールバックの条件

本書作成時点では計画のみを対象とし、実装変更は行わない。

## 2. 背景と現状認識

TDnet Digestの現行実装には、次の強みがある。

- タイトルから決算期、会計基準、連結・個別を決定論的に判定する
- 文書タイプ別に抽出項目を分ける
- 決算の増減率、進捗率、予想修正を明示的な基準で評価する
- 情報抽出と表示整形を分離した2パス要約を使用する
- `null`や欠損値を表示しないルールを持つ
- 全文抽出と要点抽出を切り替えられる

一方、投資家・トレーダー向けの分析としては、次が構造化されていない。

- 利益率とその変化
- 本業利益と一時損益の分離
- キャッシュフローと財務健全性
- 短期・中期・長期の時間軸別評価
- 好材料、リスク、次回確認点
- 各判断の根拠ページ
- 株主優待、株式分割、資本政策、事業進捗、ガバナンスの専用分析
- プロバイダー機能を利用した厳格な構造化出力
- プロンプト変更前後を比較する再現可能な評価基盤

## 3. 最終目標

利用者が原文を読む前に、以下を短時間で把握できる状態を目指す。

1. 開示された事実と主要数値
2. 前年・会社計画・従来予想に対する変化
3. 増減が本業によるものか、一時要因によるものか
4. 短期、中期、長期それぞれへの影響
5. 最大の好材料と最大のリスク
6. 次の決算までに確認すべき指標
7. 各判断を確認できるPDFページ

精度向上とは、文章を詳しくすることではなく、次の同時達成を意味する。

- 数値の正確性を維持または向上する
- 重要情報の見落としを減らす
- 根拠のない推測を増やさない
- 同じ内容の重複を減らす
- モデルやプロバイダーが変わっても出力構造を安定させる

## 4. 固定する設計原則

### 4.1 現行の数値抽出を置き換えない

現行の決算期別プロンプト、会計基準対応、経常利益ベースの明示的な判定基準は維持する。新しい投資診断は、その上に追加する。

### 4.2 事実抽出と投資評価を分離する

パス1では本文から事実と根拠を抽出する。パス2ではパス1のJSONだけを使用して表示を整形する。投資評価に必要な計算も、入力数値と計算結果を分けて保持する。

### 4.3 市場データを推測しない

PDFに記載されていない以下の情報を推測しない。

- 市場コンセンサス
- 現在株価
- バリュエーション
- 株価への織り込み度
- 将来の上方修正・下方修正の確定的予測

「サプライズ」は、会社計画比、従来予想比、前年同期比のいずれかが明示できる場合に限って使用する。

### 4.4 情報がないことを機械的に減点しない

- 好業績で予想据え置きの場合、据え置きだけを理由に大幅減点しない
- 非決算資料に業績数値がないことを減点しない
- 費用負担が未記載という理由だけで株主優待の効果を中立以下にしない
- 好材料やリスクが本文から確認できない場合は空配列を許可する

### 4.5 根拠を表示できない評価を増やさない

好材料、リスク、重要な数値、評価理由には、可能な限り根拠ページを付ける。ページ不明を0として埋めるのではなく、`null`として不明を明示する。

### 4.6 点数は最後に導入する

短期・中期・長期・総合の0〜100点は最終段階で実装する。評価データによる校正が完了するまでは実験機能とし、デフォルト表示しない。

### 4.7 プロバイダー互換性を維持する

OpenAI固有機能だけに全面移行しない。構造化出力はプロバイダー能力に応じて使用し、未対応時は現行のJSONプロンプトとローカル検証へフォールバックする。

### 4.8 参考実装のコードを直接移植しない

参考にするのは分析観点と設計上のアイデアに限定する。TDnet Digestの型、2パス構成、UI、セキュリティ要件に合わせて独立に実装する。

## 6. 目標データフロー

```text
TDnetタイトル
  ↓
決定論的な一次分類
  ↓
PDFをページ単位で抽出・クリーニング
  ↓
ページ番号付きLLM入力
  ↓
パス1: 文書タイプ別の事実抽出JSON
  ↓
ランタイム検証・計算整合性チェック
  ↓
必要時のみ修復再試行
  ↓
パス2: JSONから表示用Markdownへ整形
  ↓
安全なMarkdown表示・ページ根拠リンク表示
  ↓
分析バージョン付きキャッシュ
```

分類が`other`または曖昧な場合だけ、軽量な再分類を行う。最初から全資料をLLM分類にはしない。

## 7. 文書タイプの拡張

`DocumentType`を次の11種類へ拡張する。

| 型                   | 用途                   | 現行からの変更 |
| -------------------- | ---------------------- | -------------- |
| `earnings`           | 決算短信               | 維持・強化     |
| `earningsRevision`   | 業績予想修正           | 維持・強化     |
| `shareholderBenefit` | 株主優待               | 新規           |
| `dividend`           | 配当・増配・減配       | 維持・強化     |
| `shareRepurchase`    | 自己株式取得           | 維持・強化     |
| `stockSplit`         | 株式分割・併合         | 新規           |
| `capitalPolicy`      | 資本政策・資本業務提携 | 新規           |
| `ma`                 | M&A・組織再編          | 維持・強化     |
| `businessUpdate`     | 月次・受注・事業進捗   | 新規           |
| `governance`         | 役員・ガバナンス       | 新規           |
| `other`              | 上記以外               | 維持           |

### 7.1 分類方針

1. タイトルの明確なキーワードで決定論的に分類する
2. 複数条件が一致する場合の優先順位をテストで固定する
3. `other`または競合時のみ、PDF先頭ページを使った補助分類を検討する
4. LLMの補助分類結果だけで専用スキーマを選び直す場合は、追加API呼び出しと誤分類リスクを計測する
5. 分類不能時は無理に専用型へ寄せず、`other`を使用する

## 8. ページ境界と根拠情報

### 8.1 内部型

PDF抽出結果を単一文字列だけで扱わず、次のページ配列を正とする。

```ts
interface ExtractedPage {
  pageNumber: number;
  text: string;
}

interface PdfExtractionResult {
  pages: ExtractedPage[];
  metadata: SummaryMetadata;
}
```

### 8.2 LLM入力形式

各ページを曖昧でない境界で連結する。

```text
[PDF_PAGE:1]
...

[PDF_PAGE:2]
...
```

ページ本文に数字だけの行が存在してもページ境界と混同しない形式にする。

### 8.3 根拠型

```ts
interface EvidenceFact {
  text: string;
  page: number | null;
}
```

ページ番号はPDF上の1始まりとする。存在しないページ番号、抽出対象外ページ、0以下の値は検証エラーとする。根拠が特定できない場合は`null`を許可する。

## 9. 決算抽出スキーマの拡張

現行の`EarningsExtraction`を土台に、以下を追加する。

```ts
interface EarningsQuality {
  operatingMargin: {
    current: string | null;
    previous: string | null;
    change: string | null;
    page: number | null;
  } | null;
  coreEarnings: EvidenceFact | null;
  oneOffItems: EvidenceFact[];
  operatingCashFlow: EvidenceFact | null;
  financialHealth: EvidenceFact[];
  shareholderReturns: EvidenceFact[];
}

type InvestmentStance =
  | 'positive'
  | 'slightlyPositive'
  | 'neutral'
  | 'slightlyNegative'
  | 'negative'
  | 'unknown';

interface HorizonAssessment {
  stance: InvestmentStance;
  rationale: EvidenceFact[];
}

interface InvestmentView {
  shortTerm: HorizonAssessment;
  mediumTerm: HorizonAssessment;
  longTerm: HorizonAssessment;
  positives: EvidenceFact[];
  risks: EvidenceFact[];
  watchPoints: EvidenceFact[];
  rationale: string;
}
```

### 9.1 決算の分析規則

#### 短期

- 前年同期比の売上・利益モメンタム
- 会社計画または従来予想に対する変化
- 上方修正・下方修正・据え置き
- 一時損益を除いた本業の方向
- 配当・自己株式取得など同時発表の株主還元

#### 中期

- 通期予想への進捗
- 利益率の改善・悪化
- セグメント別の持続性
- 受注、月次、パイプライン、新規出店などの先行指標
- 会社説明にある需要・コスト・為替の継続性

#### 長期

- 事業構造と成長ドライバー
- 収益源の分散または集中
- 営業CFと投資負担
- 自己資本、ネットキャッシュ、継続企業リスク
- 資本政策と株主還元の持続性

### 9.2 据え置き予想の規則

- 据え置きは事実として記載する
- 据え置きだけを理由に短期・中期評価を大幅に下げない
- 進捗が高くても上方修正を予測しない
- 「上方修正余地」ではなく「次回確認点」として扱う

### 9.3 一時損益の規則

- 営業利益・事業利益・経常利益など本業に近い利益と、純利益を分けて評価する
- 特別利益で純利益だけが増加した場合、利益の質に注意を付ける
- 本業が改善している場合は、一時利益の存在だけで全体を悪化判定しない
- 特別損失は内容、金額、継続性を分けて記載する

### 9.4 進捗率の規則

- 現行の計算式とレンジ予想対応を維持する
- Q1=25%、Q2=50%、Q3=75%は参考基準であり、季節性を無視した絶対評価にしない
- 前年同期進捗が得られる場合は、標準進捗率より優先度の高い補助情報として表示する
- 赤字予想、ゼロ予想、未定は既存ルールに従って算出不能とする

## 10. 非決算文書の専用分析

### 10.1 株主優待

- 変更前後の実質価値
- 対象保有株数と保有期間
- 拡充・縮小の対象範囲
- 開始日・基準日
- 継続保有条件
- 株主獲得・定着効果
- 会社負担と継続性

### 10.2 株式分割・併合

- 分割・併合比率
- 基準日・効力発生日
- 投資単位への影響
- 発行可能株式総数の変更
- 配当予想の実質変更有無
- 株主価値そのものは分割だけでは増加しないことを明示

### 10.3 資本政策・資本業務提携

- 調達額、希薄化率、割当先
- 資金使途
- 提携内容と実行時期
- 資本効率への影響
- 希薄化と成長投資のバランス

### 10.4 事業進捗・月次

- 前年同月比、累計前年同期比
- 既存店・全店、数量・単価の区別
- 受注・受注残・解約・稼働率など業種別KPI
- 一過性要因と基調
- 通期計画との関係は本文に根拠がある場合のみ記載

### 10.5 ガバナンス

- 役員変更、独立性、委員会構成
- 不祥事・内部統制・再発防止策
- 施行日と移行期間
- 業績影響を無理に推測しない

## 11. 構造化出力と検証

### 11.1 プロバイダー能力の抽象化

LLMクライアントに、少なくとも次の能力判定を設ける。

```ts
interface ProviderCapabilities {
  nativeJsonSchema: boolean;
  jsonMode: boolean;
  toolUse: boolean;
}
```

優先順位は次とする。

1. ネイティブJSON Schema
2. JSONモード + ローカルスキーマ検証
3. 現行のJSONプロンプト + ローカルスキーマ検証

### 11.2 ランタイム検証

TypeScript型だけに依存せず、パス1の結果を実行時に検証する。

検証対象:

- 必須フィールド
- 列挙値
- 配列上限
- ページ番号の範囲
- 数値文字列の形式
- `null`と文字列`"null"`の混同
- 同一内容の重複
- 進捗率の再計算結果との不一致

### 11.3 修復方針

- JSON構文エラーまたは軽微なスキーマエラーは、検証エラーを添えて1回だけ修復再試行する
- 本文を再送せず、壊れたJSONと検証エラーだけで修復できる場合はそれを優先する
- 数値の根拠不足やページ不整合は、表示整形で隠さない
- 修復後も失敗した場合は、品質警告付きで安全な最小表示へフォールバックする
- パス1の未検証テキストを正常な分析結果としてそのまま表示しない

## 12. 表示仕様

決算の標準表示順を次で固定する。

1. 全体要約
2. 現行の決算評価
3. 業績サマリー
4. 通期進捗・予想修正
5. 利益の質
6. 短期・中期・長期の見方
7. 好材料
8. リスク
9. 次回確認点
10. トピックス

### 12.1 表示制約

- 全体要約は最大3文を基本とする
- 好材料とリスクは各最大2件
- 次回確認点は最大3件
- 同一事実を複数セクションで言い換えて繰り返さない
- 根拠ページがある項目は`p.3`形式で表示する
- 根拠ページをクリック可能にする機能は別途可否を調査する
- 空のセクションは見出しごと表示しない
- 「本文に記載なし」を埋めるためだけの行は作らない

## 13. 実験的スコアリング

### 13.1 導入条件

以下を満たすまで、0〜100点をデフォルト表示しない。

- 評価コーパスが整備されている
- 複数モデルでスコア分布を比較済み
- 同一PDFを3回実行したときの変動を計測済み
- 50点、60点、70点、80点、90点の意味を具体例で校正済み
- 点数理由を根拠ページ付きで説明できる

### 13.2 スコア定義

- 50点を中立とする
- 短期、中期、長期、総合を別々に持つ
- 総合点を3期間の単純平均にはしない
- 文書タイプごとに評価軸を変える
- 最大の加点要因と減点要因を必須とする
- 好材料・リスクが存在しない場合に、それらを捏造して点数理由を作らない

### 13.3 ロールアウト

1. 開発者向けデバッグ表示
2. 設定画面の実験機能
3. 評価結果を確認後、一般設定へ昇格

## 14. キャッシュ設計

現行のPDF URLだけによるキャッシュキーでは、プロンプトやスキーマ更新後も古い結果が表示される。次をキーまたはエントリへ含める。

- `analysisSchemaVersion`
- PDF URL
- プロバイダー
- モデル
- 抽出モード
- 要約モード
- 将来のスコアリング設定

旧キャッシュは読み込み時にバージョン不一致を検出し、再分析を案内する。無条件に破棄するか移行するかは、データ構造確定時に決める。

## 15. 評価計画

### 15.1 評価コーパス

最低36件を用意する。

#### 決算 24件以上

- Q1、Q2、Q3、通期
- 日本基準、IFRS、可能なら米国基準
- 増収増益、減収増益、減収減益
- 黒字転換、赤字転落、赤字継続
- 上方修正、下方修正、据え置き、予想未定
- レンジ予想
- 特別利益・特別損失
- 強い季節性
- 初連結、新規上場、会計基準変更

#### 非決算 12件以上

- 業績修正
- 配当
- 自己株式取得
- 株主優待
- 株式分割
- M&A
- 資本政策
- 月次・事業進捗
- ガバナンス

PDFそのものをリポジトリへ追加できない場合は、出典URL、取得日、タイトル、期待値JSON、ページ単位の抽出テキストを管理する。APIキーや非公開資料は含めない。

### 15.2 正解データ

各資料について、人手で次を作成する。

- 正しい文書タイプ
- 主要数値と単位
- 前年同期比・前期比
- 通期予想と進捗率
- 予想修正
- 一時損益
- 利益率
- CF・財務情報
- 株主還元
- 根拠ページ
- 好材料、リスク、確認点の許容例

### 15.3 評価指標

| 指標                       | 必須合格条件          | 目標        |
| -------------------------- | --------------------- | ----------- |
| 文書分類正解率             | 95%以上               | 98%以上     |
| 売上・主要利益の数値一致率 | 98%以上               | 99%以上     |
| 進捗率計算                 | 計算可能ケースで100%  | 100%        |
| 予想修正方向               | 98%以上               | 100%        |
| 根拠ページ一致率           | 95%以上               | 98%以上     |
| 重大な数値捏造             | 0件                   | 0件         |
| JSON構造成功率             | 99%以上               | 100%        |
| 同一情報の重複             | 現行以下              | 現行比50%減 |
| 人手による有用性比較       | 改善版が60%以上で優位 | 70%以上     |

### 15.4 比較条件

- 同じPDF抽出結果を使用する
- 同じモデルと同じ設定で比較する
- キャッシュを使用しない
- 安定性評価では各PDFを3回実行する
- 現行版、改善版の表示順を伏せて評価する
- コストと処理時間も記録する

## 16. 実装フェーズ

## 17. テスト方針

### 17.1 単体テスト

- 文書タイプ判定と優先順位
- 決算期・会計基準・連結区分判定
- ページ境界の生成と保持
- ページ番号範囲検証
- 進捗率とレンジ予想計算
- JSONスキーマ検証
- `null`処理
- 重複排除
- キャッシュバージョン判定
- 表示用Markdown生成

### 17.2 統合テスト

- PDF抽出からパス1入力まで
- モックLLMレスポンスからパス2表示まで
- JSON破損時の修復再試行
- プロバイダー能力別フォールバック
- smart/full切り替え
- 旧キャッシュからの移行

### 17.3 手動確認

- TDnet一覧のiframe再読み込み
- 要約、表示、非表示、再要約
- 根拠ページ表示
- 長い社名・タイトル
- 大量ページPDF
- 画像PDFエラー
- 日本基準・IFRSの表示差

## 18. リリース戦略

大きな一括リリースにはせず、各Phaseを独立した変更として進める。

1. 評価基盤はユーザー機能と分離して先行導入
2. ページ境界と分類は、表示を変えず内部変更として導入
3. 新しい分析セクションは設定フラグ付きで導入
4. 評価指標を満たした後にデフォルト有効化
5. スコアリングは最後まで実験機能として分離

各Phaseで以下を記録する。

- 変更前後の評価指標
- APIコスト
- 処理時間
- 既知の失敗例
- ロールバック方法

## 19. ロールバック条件

次のいずれかを満たした場合、そのPhaseのデフォルト有効化を見送る。

- 重大な数値捏造が1件以上発生
- 主要数値一致率が現行より低下
- 文書分類正解率が95%未満
- JSON構造成功率が99%未満
- 既存プロバイダーのいずれかが利用不能
- 平均APIコストまたは処理時間が、合意なしに50%以上増加
- 根拠ページが誤った事実へ紐付く
- 新しい評価が市場データを推測している

## 20. 実装前に確定すべき事項

Phase 0開始前に、以下だけはユーザーと合意する。

1. 評価用PDFまたはURLの準備方法
2. 正解データを誰がレビューするか
3. 初期の評価対象モデル
4. APIコストの上限
5. 実験スコアをUIへ出す時期
6. 根拠ページを単なる表示にするか、PDFページへの導線まで作るか

## 21. 完了の定義

全対応完了とは、コードが追加された状態ではなく、以下をすべて満たした状態とする。

- 11種類の文書タイプを安定して分類できる
- 決算で利益率、一時損益、CF、財務、株主還元を抽出できる
- 短期・中期・長期の見方を根拠付きで表示できる
- 好材料、リスク、確認点を重複なく表示できる
- 根拠ページを原文で確認できる
- 構造化出力を検証し、壊れた結果を正常表示しない
- プロンプト更新後に古いキャッシュを誤表示しない
- 評価コーパスで必須合格条件を満たす
- 0〜100点は校正済みかつ無効化可能である
- README、CLAUDE.md、設定画面の説明が実装と一致している
